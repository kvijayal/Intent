# MTA YAML Reviewer Skill — CAPM Best Practices
# Validated against real-world enterprise MTA files (zmmke0001_mk, zbue0004_mk)

## Mandatory Workflow

1. Read the mta.yaml file in FULL before any judgement — skim reads miss cross-reference errors
2. List every module name and every resource name first, then check cross-references
3. Identify the layout — Pattern A (generated by `deploy-config.mjs`, the default) or Pattern B (hand-written `init_data`); `.claude/skills/deployment-validation/references/mta-layouts.md` maps every rule below to where it lives in each
4. Run the quick-scan greps below to catch the two most common critical failures immediately
5. Work through each category in order, mark PASS / WARN / FAIL
6. Report using the structured output format at the end of this skill

**Fix for missing or incomplete generated content (CAP projects):** `node .claude/skills/sap-conventions/scripts/deploy-config.mjs <app>`,
then `cd <app> && npm install`. Never hand-write `mta.yaml`.

```bash
# Quick-scan — run these first, they catch the most common critical failures
grep -n "forwardAuthToken\|ForwardAuthToken" mta.yaml
# Expected: at least 2 hits — one in srv provides, one on the srv-api destination
# (Pattern A: app-deployer parameters.config.destinations; Pattern B: destination init_data)

grep -n "existing_destinations_policy" mta.yaml
# Expected: all occurrences must be 'update' — never 'ignore' or 'fail'

grep -n "npm install" mta.yaml
# Expected: zero hits — all builder commands must use 'npm ci'

grep -n "service-name:" mta.yaml
# Expected: every org.cloudfoundry.managed-service resource has one
# (a com.sap.xs.hdi-container resource needs none unless its name is referenced, DB4)

grep -n "path:" mta.yaml
# Check for 'path: ..' — points outside project root (common copy-paste error)

# CRITICAL — detect URL-based destinations placed inside destination-content module
# The GACD (Generic Application Content Deployer) only accepts service-key destinations.
# Any URL: entry inside parameters.content.instance.destinations fails at deploy time with
# "Missing destination property [ServiceInstanceName]" — move them to init_data instead.
grep -n "URL:" mta.yaml
# Cross-check: every URL: hit must be inside the app-deployer parameters.config.destinations
# (Pattern A) or a resource config.init_data block (Pattern B),
# NOT inside a module parameters.content block.
```

## Real-World Architecture — Two Valid Destination Patterns

Both patterns are correct. Identify which pattern the file uses before reviewing sections 5–8.
They are layouts A and B of `deployment-validation` → `references/mta-layouts.md` (names, rule-to-location map, verified reference output).

### Pattern A — Generated (`cds add mta,workzone-standard` via `deploy-config.mjs`, the default)
The **srv-api HTTP destination** lives in the **app-deployer module** `parameters.config.destinations`
(`Name: srv-api`); the app-deployer `requires` lists `srv-api`, and its html5-repo-host entry carries
`parameters.config.HTML5Runtime_enabled: true`.
**Service-binding destinations** (OAuth2UserTokenExchange, html5-repo) live in the `<id>-destinations`
module `parameters.content`. The destination resource has no `init_data` and there is no `ui5` destination.

### Pattern B — Split (hand-written, enterprise, multi-service)
**HTTP destinations** (srv-api, ui5) live in the **destination RESOURCE** `init_data`.
**Service-binding destinations** (OAuth2UserTokenExchange, html5-repo) live in the **destination-content MODULE** `parameters.content`.
The destination resource has `requires: - name: srv-api` so `~{srv-api/srv-url}` resolves correctly.

Both real-world files reviewed used Pattern B. Both patterns require the same `forwardAuthToken` checks.

### 0. General Pre-Checks

| # | Rule | Severity |
|---|------|----------|
| G1 | No module of `type: approuter.nodejs` — the standalone approuter pattern is superseded by the `html5-apps-repo` pattern (BTP HTML5 Application Runtime). Flag and recommend migration. | WARN |
| G2 | Every module `name` referenced in any `requires` block must exist as a declared module or resource `name`, or as a `provides` name (e.g. `srv-api`) — dangling references fail at deploy time with no clear error | FAIL |

### 1. Header & Schema

| # | Rule | Severity |
|---|------|----------|
| H1 | `_schema-version` must be `"3.3"` or `"3.3.0"` as a **quoted string** — unquoted `3.3` is parsed as a float by YAML and rejected by MBT at build time. Unquoted `3.3.0` (what `cds add mta` writes) is a YAML string too and PASSES | FAIL |
| H2 | `ID` must be present, lowercase, and globally unique within the BTP global account | WARN |
| H3 | `version` must follow semver (`1.0.0`) | WARN |
| H4 | `description` must NOT be `"A simple CAP project."` — the auto-generated placeholder seen in both reviewed files | WARN |
| H5 | `parameters.enable-parallel-deployments: true` must be present for faster deployments | WARN |
| H6 | For fullstack apps, `parameters.deploy_mode: html5-repo` must be set at the top level | WARN |

---

### 2. Build Parameters

| # | Rule | Severity |
|---|------|----------|
| B1 | `before-all` block must exist under `build-parameters` | FAIL |
| B2 | `builder: custom` must be set on the `before-all` entry | FAIL |
| B3 | First command must be `npm ci` — never `npm install` (ignores lock file, non-deterministic) | FAIL |
| B4 | Second command must be `npm exec --no -- cds build --production` — sole CDS compilation step. `npx` installs from npm when the project has no local `@sap/cds-dk`, and the npm package literally named `cds` is an unrelated project; `npm exec --no` runs the local bin or fails, it never downloads. The same command with an `npx` prefix (what `cds add mta` writes) is a WARN, not a FAIL — fix: `node .claude/skills/sap-conventions/scripts/stack.mjs apply <app> --scope deploy` (rewrites the line) | FAIL (`npx` form: WARN) |
| B5 | Commands must be in ORDER: `npm ci` THEN `npm exec --no -- cds build --production` (or the `npx`-prefixed form, see B4) | FAIL |
| B6 | No additional `cds build` anywhere else in the file — in any form (`npm exec --no -- cds build`, `npx`-prefixed, or bare `cds build`) | FAIL |

**Correct pattern:**
```yaml
build-parameters:
  before-all:
    - builder: custom
      commands:
        - npm ci
        - npm exec --no -- cds build --production
```

### 3. srv Module (CAP Node.js Service)

> **HANA conditionality:** Rules S7 and S8 apply only when the app has a HANA HDI container resource. Skip them for SQLite-only apps or apps that consume only external OData without a local DB.

**This section contains the single most commonly missed rule (S6 — forwardAuthToken). Check it first.**

| # | Rule | Severity |
|---|------|----------|
| S1 | `type: nodejs` | FAIL |
| S2 | `path: gen/srv` — NEVER `srv/` or `./srv` — deploys compiled artefact, not source | FAIL |
| S3 | `build-parameters.builder: npm-ci` — never `npm` or `npm-install` | FAIL |
| S4 | `provides` block must exist with an entry named `srv-api` | FAIL |
| S5 | `srv-api` entry must have `srv-url: ${default-url}` | FAIL |
| S6 | **`srv-api` entry MUST have `forwardAuthToken: true`** — omitting this strips the JWT before it reaches CAP; RBAC silently returns 403 on every request even with a valid user token. Found missing in BOTH real-world files reviewed. | FAIL |
| S7 | `requires` must list the HANA HDI container resource | FAIL |
| S8 | `requires` must list the XSUAA resource | FAIL |
| S9 | `parameters.buildpack: nodejs_buildpack` | WARN |
| S10 | `parameters.memory` is optional in the base `mta.yaml` — absent means the space default applies (Pattern A omits it, PASS); set it in `.mtaext` per environment when that default is too low (`1024M` is typical for production). WARN only when it is set below `256M` | WARN |
| S12 | `parameters.instances` should be `1` in base `mta.yaml`; use `.mtaext` for production scale-out | WARN |
| S13 | `build-parameters.ignore: ["node_modules/"]` prevents local node_modules being included in the archive. Needed only when `path` is a source folder: with `path: gen/srv` the before-all build writes that folder fresh, so Pattern A without `ignore` PASSES | WARN |

**Correct srv module pattern:**
```yaml
- name: <app-id>-srv
  type: nodejs
  path: gen/srv
  parameters:
    instances: 1
    buildpack: nodejs_buildpack
    memory: 1024M
    disk-quota: 1G
  build-parameters:
    builder: npm-ci
    ignore:
      - "node_modules/"
  provides:
    - name: srv-api
      properties:
        forwardAuthToken: true       # ← CRITICAL — JWT forwarding to CAP
        srv-url: ${default-url}
  requires:
    - name: <app-id>-auth            # XSUAA
    - name: <app-id>-db              # HANA HDI
    - name: <app-id>-destination
    - name: <app-id>-connectivity    # only if on-premise systems exist
```

Pattern A writes the same module without `memory`, `disk-quota` and `ignore` — also correct (S10, S13).

### 4. db-deployer Module (HANA HDI Deployer)

> **Conditional section:** Applies only when the app has a HANA HDI container resource (`type: com.sap.xs.hdi-container`). If the app uses SQLite or no local DB, skip this section entirely.

| # | Rule | Severity |
|---|------|----------|
| D1 | `type: hdb` | FAIL |
| D2 | `path: gen/db` — never `db/` | FAIL |
| D3 | `requires` must list the HANA HDI container resource | FAIL |
| D4 | `parameters.buildpack: nodejs_buildpack` | WARN |
| D5 | If the HANA resource uses the `hdi-container-name` property pattern, db-deployer must bind it via `TARGET_CONTAINER: ~{hdi-container-name}` | FAIL |

**Standard pattern:**
```yaml
- name: <app-id>-db-deployer
  type: hdb
  path: gen/db
  parameters:
    buildpack: nodejs_buildpack
  requires:
    - name: <app-id>-db
```

**With `hdi-container-name` property binding (multi-container or explicit schema):**
```yaml
- name: <app-id>-db-deployer
  type: hdb
  path: gen/db
  parameters:
    buildpack: nodejs_buildpack
  requires:
    - name: <app-id>-db
      properties:
        TARGET_CONTAINER: ~{hdi-container-name}    # resolves from HANA resource properties
```

### 5. UI Modules (Fullstack apps — multiple apps supported)

Each UI5/Fiori app is a separate module of `type: html5`. Real enterprise apps have multiple UI modules.

| # | Rule | Severity |
|---|------|----------|
| U1 | Each UI module `type` must be `html5` | FAIL |
| U2 | `build-parameters.builder: custom` on each UI module | FAIL |
| U3 | Builder commands never use `npm install` (FAIL). Install step: a UI app covered by the root `package.json` `workspaces` runs only its build script — the before-all `npm ci` installs it; its own `npm ci` there = WARN (reinstalls the whole tree without the root packages). An app outside the workspaces runs `npm ci` first (missing = WARN) | FAIL / WARN |
| U4 | `build-parameters.build-result: dist` on each UI module | WARN |
| U5 | `supported-platforms: []` must be set to prevent CF default platform deployment | WARN |
| U6 | Each UI module must be listed in the app-deployer's `build-parameters.requires` with its artifact zip and `target-path` | FAIL |
| U7 | Each UI module whose app is served by the CAP project has the `relative-odata-uri` build task in the ui5 config its build script uses (`app/<folder>/ui5.yaml` in Pattern A, `ui5-deploy.yaml` in Pattern B), resolvable through the extension package `app/<folder>/ui5-tasks/relative-odata-uri/` and its `file:` devDependency `ui5-task-relative-odata-uri` — or another build step that makes the BUILT dataSources uri relative. Without it the deployed app requests `/odata/...` without the app path: 404 on every OData call in SAP Build Work Zone. Fix: `deploy-config.mjs` (see Mandatory Workflow) | FAIL |
| U8 | The SOURCE `app/<folder>/webapp/manifest.json` of a CAP-served app keeps the absolute dataSources uri `/odata/v4/<svc>/`. A relative uri there (bare `odata/...` or `<destination>/odata/...`) breaks `cds watch` (404 at `/<namespace>/odata/...`); the deployed form comes from U7 | FAIL |

The html5 module name is free; Pattern A names it `<ID without dashes><app folder>` (e.g. `leaveappleaverequests` for ID `leave-app` and `app/leaverequests`).

**Correct UI module pattern:**
```yaml
- name: <ui-module-name>
  type: html5
  path: app/<ui-folder-name>
  build-parameters:
    build-result: dist
    builder: custom
    commands:
      - npm run build            # workspace app: no own npm ci (before-all installs it); never npm install
    supported-platforms: []
```

### 6. App-Deployer Module (Fullstack apps)

Uploads all UI5 zip artefacts to the HTML5 Application Repository.

| # | Rule | Severity |
|---|------|----------|
| AD1 | `type: com.sap.application.content` | FAIL |
| AD2 | `requires` must list the html5-repo-host resource with `content-target: true` | FAIL |
| AD3 | `build-parameters.build-result` must point to the folder where zips land (e.g. `app/`) | FAIL |
| AD4 | `build-parameters.requires` must list every UI module with its artifact zip name and `target-path` | FAIL |
| AD5 | `path: gen` (when using cds build output) or `.` for source-based builds | WARN |

In Pattern A the app-deployer also holds the srv-api destination; DS4, DS7–DS10, DS12 and J2 are then checked here (see 8d).

**Correct app-deployer pattern (multiple UI apps; the commented lines are Pattern A):**
```yaml
- name: <app-id>-app-deployer
  type: com.sap.application.content
  path: gen
  requires:
    - name: <app-id>-auth                  # Pattern A
    - name: srv-api                        # Pattern A: needed for ~{srv-api/srv-url} below
    - name: <app-id>-html5-repo-host
      parameters:
        content-target: true
        config:                            # Pattern A
          HTML5Runtime_enabled: true
  parameters:                              # Pattern A: the srv-api destination
    config:
      destinations:
        - Name: srv-api
          URL: ~{srv-api/srv-url}
          Authentication: NoAuthentication
          Type: HTTP
          ProxyType: Internet
          HTML5.ForwardAuthToken: true
          HTML5.DynamicDestination: true
  build-parameters:
    build-result: app/
    requires:
      - name: <ui-module-1>
        artifacts:
          - <ui-module-1-bundle>.zip
        target-path: app/
      - name: <ui-module-2>
        artifacts:
          - <ui-module-2-bundle>.zip
        target-path: app/
```

### 7. Destination-Content Module (Fullstack apps)

Configures service-binding destinations in the BTP Destination Service. HTTP destinations live in the app-deployer `parameters.config.destinations` (Pattern A, Section 6) or in the destination **resource** `init_data` (Pattern B, Section 8d) instead. Pattern A names this module `<app-id>-destinations`, Pattern B usually `<app-id>-destination-content`.

| # | Rule | Severity |
|---|------|----------|
| DC1 | `type: com.sap.application.content` | FAIL |
| DC2 | `path` absent (Pattern A, with `no-source: true`) or `.` — **never `..`** (parent directory causes `ENOENT` during `mbt build`) | FAIL |
| DC3 | `build-parameters.no-source: true` must be set | FAIL |
| DC4 | `requires` must include destination resource with `content-target: true` | FAIL |
| DC5 | `requires` must include XSUAA resource with `service-key` | FAIL |
| DC6 | `requires` must include html5-repo-host resource with `service-key` | FAIL |
| DC7 | `requires` must include `srv-api` (Pattern A, where the app-deployer lists it too) OR the `requires` of the destination resource must include `srv-api` (Pattern B) — one location must reference it | FAIL |
| DC8 | `parameters.content.instance.existing_destinations_policy` must be `update` — **never `ignore` or `fail`** | FAIL |
| DC9 | OAuth2UserTokenExchange destinations must reference the correct `ServiceInstanceName` matching the resource's explicit `service-name` | FAIL |
| DC10 | `ServiceInstanceName` for html5-repo-host must match the explicit `service-name` on that resource | FAIL |
| DC11 | `sap.cloud.service` in every destination-content destination must match the `sap.cloud.service` value in each UI app's `manifest.json` — mismatch means the HTML5 Runtime cannot associate the app with the correct service instance | FAIL |
| DC12 | **No `URL:` property inside any `parameters.content.instance.destinations` entry.** The Generic Application Content Deployer (GACD) only handles service-key destinations (`ServiceInstanceName` + `ServiceKeyName`). Any entry with a `URL:` key causes the deploy to fail immediately with `Missing destination property [ServiceInstanceName]`. Move URL-based destinations (srv-api, ui5 CDN) to the app-deployer `parameters.config.destinations` (Pattern A — rerun `deploy-config.mjs`) or the destination **resource** `config.init_data` block (Pattern B). | FAIL |

**Correct destination-content module pattern (service-binding destinations only; names as Pattern A generates them):**
```yaml
- name: <app-id>-destinations
  type: com.sap.application.content
  # no path in Pattern A; Pattern B: path: .  (never a parent path)
  requires:
    - name: <app-id>-auth
      parameters:
        service-key:
          name: <app-id>-auth-key
    - name: <app-id>-html5-repo-host
      parameters:
        service-key:
          name: <app-id>-html5-repo-host-key
    - name: srv-api
    - name: <app-id>-destination
      parameters:
        content-target: true
  build-parameters:
    no-source: true
  parameters:
    content:
      instance:
        existing_destinations_policy: update   # ← never 'ignore' or 'fail'
        destinations:
          - Name: <app-id>-html5-repository
            ServiceInstanceName: <app-id>-html5-repo-host  # must match service-name on resource
            ServiceKeyName: <app-id>-html5-repo-host-key
            sap.cloud.service: <app-id>.service
          - Name: <app-id>-auth
            Authentication: OAuth2UserTokenExchange
            ServiceInstanceName: <app-id>-auth             # must match service-name on resource
            ServiceKeyName: <app-id>-auth-key
            sap.cloud.service: <app-id>.service
```

### 8. Resources

#### 8a. XSUAA Resource

| # | Rule | Severity |
|---|------|----------|
| X1 | `type: org.cloudfoundry.managed-service` | FAIL |
| X2 | `parameters.service: xsuaa` | FAIL |
| X3 | `parameters.service-plan: application` | FAIL |
| X4 | `parameters.service-name` must be explicitly set — used as `ServiceInstanceName` in destination-content module | FAIL |

**Correct XSUAA pattern (as Pattern A generates it):**
```yaml
- name: <app-id>-auth
  type: org.cloudfoundry.managed-service
  parameters:
    service: xsuaa
    service-plan: application
    service-name: <app-id>-auth
    path: ./xs-security.json
    config:
      xsappname: <app-id>-${org}-${space}
      tenant-mode: dedicated
      oauth2-configuration:
        credential-types:
          - binding-secret
          - x509
```

#### 8b. HANA HDI Container Resource

| # | Rule | Severity |
|---|------|----------|
| DB1 | `type: com.sap.xs.hdi-container` | FAIL |
| DB2 | `parameters.service: hana` | FAIL |
| DB3 | `parameters.service-plan: hdi-shared` | FAIL |
| DB4 | `parameters.service-name` is optional on a `com.sap.xs.hdi-container` resource: without it the deployer names the instance after the resource, and Pattern A omits it (PASS). It is required when something references the instance name (DB5 `${service-name}`, a `ServiceInstanceName`). Keep the resource name and any `service-name` stable across deploys — a changed name creates a new, empty HDI container | FAIL |
| DB5 | If `properties: hdi-container-name: ${service-name}` is used, `service-name` is doubly critical — `${service-name}` resolves to this value and the db-deployer uses it for `TARGET_CONTAINER` binding | FAIL |

**Correct HANA pattern (with property binding):**
```yaml
- name: <APP-ID>-db
  type: com.sap.xs.hdi-container
  parameters:
    service: hana
    service-plan: hdi-shared
    service-name: <app-id>-hdi-container    # ← REQUIRED — ${service-name} resolves to this
    config:
      schema: <APP-ID>
  properties:
    hdi-container-name: ${service-name}     # exposed for TARGET_CONTAINER in db-deployer
```

| # | Rule | Severity |
|---|------|----------|
| HR1 | `parameters.service-plan: app-host` — stores static app artefacts | FAIL |

#### 8d. Destination Service Resource

"The srv-api destination" below is the srv-api HTTP destination wherever the pattern keeps it: the
app-deployer `parameters.config.destinations` (Pattern A) or this resource `config.init_data` (Pattern B).

| # | Rule | Severity |
|---|------|----------|
| DS1 | `parameters.service: destination` | FAIL |
| DS2 | `parameters.service-plan: lite` — use `standard` only if on-premise connectivity required | WARN |
| DS3 | `parameters.service-name` must be explicitly set | FAIL |
| DS4 | `HTML5Runtime_enabled: true` — required for HTML5 Runtime to resolve destinations by name. Pattern A: on the app-deployer `requires` entry for the html5-repo-host (`parameters.config`); Pattern B: this resource `parameters.config` | FAIL |
| DS6 | In Pattern B: `parameters.config.init_data.instance.existing_destinations_policy: update` must be set | FAIL |
| DS7 | The srv-api destination must have `HTML5.ForwardAuthToken: true` | FAIL |
| DS8 | The srv-api destination must have `HTML5.DynamicDestination: true` | FAIL |
| DS9 | `HTML5.Timeout` on the srv-api destination — needed when the service has bulk or long-running operations (default 30s → 504). Absent on a service without such operations (Pattern A default) PASSES | WARN |
| DS10 | The srv-api destination has `URL: ~{srv-api/srv-url}` — never hardcode the CAP service URL | FAIL |
| DS11 | A `ui5` destination to `https://ui5.sap.com` is optional (Pattern A has none, PASS). When present it must NOT have ForwardAuthToken | WARN |
| DS12 | The module or resource that holds the srv-api destination must have `requires: - name: srv-api` for `~{srv-api/srv-url}` substitution (Pattern A: app-deployer; Pattern B: this resource) | FAIL |
| DS_XS1 | The srv-api destination `Name` (Pattern A `srv-api`, Pattern B usually `<app-id>-srv-api`) must exactly match the `destination` field in the `xs-app.json` OData route of each UI app — a mismatch causes the HTML5 Runtime to return 404 with no informative error message | FAIL |

**Correct destination resource (Pattern A — no `init_data`, the srv-api destination sits in the app-deployer):**
```yaml
- name: <app-id>-destination
  type: org.cloudfoundry.managed-service
  parameters:
    service: destination
    service-name: <app-id>-destination
    service-plan: lite
  requires:
    - name: srv-api
```

**Correct destination resource (Pattern B):**
```yaml
- name: <app-id>-destination
  type: org.cloudfoundry.managed-service
  parameters:
    service: destination
    service-plan: lite
    service-name: <app-id>-destination-service
    config:
      HTML5Runtime_enabled: true
      version: 1.0.0
      init_data:
        instance:
          existing_destinations_policy: update
          destinations:
            - Authentication: NoAuthentication
              HTML5.DynamicDestination: true
              HTML5.ForwardAuthToken: true
              HTML5.Timeout: 600000            # ← prevents 504 on bulk ops
              Name: <app-id>-srv-api
              ProxyType: Internet
              Type: HTTP
              URL: ~{srv-api/srv-url}
            - Authentication: NoAuthentication
              Name: ui5
              ProxyType: Internet
              Type: HTTP
              URL: https://ui5.sap.com
              # ← no ForwardAuthToken on ui5 — it is a public CDN
  requires:
    - name: srv-api                            # ← required for ~{srv-api/srv-url} substitution
```

#### 8f. Job Scheduler (Conditional)

**Skip this entire section if `grep -q "jobscheduler" mta.yaml` returns no match.**

Applies when the app uses background scheduled jobs.

| # | Rule | Severity |
|---|------|----------|
| JS1 | `parameters.service: jobscheduler` | FAIL |
| JS2 | `parameters.service-plan: standard` — `lite` plan does not support XSUAA token exchange | FAIL |
| JS3 | `parameters.config.enable-xsuaa-support: true` — required for the scheduler to obtain tokens | FAIL |
| JS4 | `parameters.service-name` must be explicitly set | WARN |

**Correct job scheduler pattern:**
```yaml
- name: <app-id>-jobscheduler
  type: org.cloudfoundry.managed-service
  parameters:
    service: jobscheduler
    service-plan: standard
```

## Antipattern Reference (from real-world reviews)

| Antipattern | Real-World Impact | Fix |
|-------------|-------------------|-----|
| Missing `forwardAuthToken: true` in srv provides | Every OData call returns 401/403 despite valid JWT — found in BOTH reviewed enterprise files | Add to `provides.srv-api.properties` |
| `path: ..` on destination-content module | `mbt build` fails with ENOENT — points outside project root | Change to `path: .` |
| `existing_destinations_policy: ignore` | Stale service keys after XSUAA/HTML5 recreation — silent binding failures | Change to `update` |
| `existing_destinations_policy: fail` | `cf deploy` fails on every redeploy after the first | Change to `update` |
| `npm install` instead of `npm ci` in any builder | Non-deterministic builds — package-lock.json ignored, version drift | Change to `npm ci` everywhere |
| HANA resource (or its `service-name`) renamed after the first deploy | A new, empty HDI container is created on the next deploy — the data stays in the old one | Keep the resource name and any `service-name` stable; a missing `service-name` alone is fine (DB4) |
| Missing `service-name` on html5-repo-host | `ServiceInstanceName` reference in destination-content silently breaks on rename | Add explicit `service-name` |
| `srv path: srv/` | Deploys source, not compiled artefact — CDS services fail to start | Change to `gen/srv` |
| `srv builder: npm` | CF downloads dev dependencies — slow builds, security risk | Change to `npm-ci` |
| `instances: 2` hardcoded in base mta.yaml | Wastes dev/QA resources, defeats environment parity | Move to `.mtaext`, set base to `1` |
| No `HTML5.Timeout` on srv-api destination of a service with bulk/long-running operations (DS9) | Default 30s timeout causes 504 on bulk/long-running CAP operations | Set `HTML5.Timeout: 600000` |
| Hardcoded CAP URL in destination | Breaks after restage/redeploy when CF assigns new URL | Use `~{srv-api/srv-url}` |
| `HTML5.ForwardAuthToken` on `ui5` destination | Security risk — forwards user tokens to a public CDN | Remove from ui5 destination |
| Connectivity service when no on-premise systems | Unnecessary service binding, billing, attack surface | Remove resource and requires binding |
| URL-based destination (`URL:`) inside `destination-content` module `parameters.content.instance.destinations` | Deploy fails immediately: `Missing destination property [ServiceInstanceName] in destination <name>`. The GACD only handles service-key destinations. Adding `Type: HTTP` or `ProxyType` does NOT fix this — the destination type is architecturally wrong. | Rerun `deploy-config.mjs` (Pattern A keeps the srv-api destination in the app-deployer `parameters.config.destinations`), or move the entry to the destination **resource** `config.init_data` and add `requires: - name: srv-api` to the resource (Pattern B) |
| CAP UI module without the `relative-odata-uri` build task (U7) | Works with `cds watch`; in SAP Build Work Zone every OData call returns 404 (absolute uri loses the app path) | Rerun `deploy-config.mjs`, then `npm install` in the app |
| Relative dataSources uri in the CAP source manifest (U8) | `cds watch` requests `/<namespace>/odata/...` → 404, blank page | Restore `/odata/v4/<svc>/`; the build task makes the deployed copy relative |
| User-provided service not pre-created in CF space | `cf deploy` fails with binding error — no clear error message | Document as pipeline prerequisite |
| Job scheduler on `lite` plan | Lite plan has no XSUAA support — token exchange fails silently | Use `standard` plan |
| Commented webIDE properties in destinations | Legacy SAP Web IDE config, deprecated — noise in the file | Remove the commented lines |
| Inline `xs-security.json` in mta.yaml | Hard to maintain, version-controlled separately for a reason | Reference via `path: ./xs-security.json` |
