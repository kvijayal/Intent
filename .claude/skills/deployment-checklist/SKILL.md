# Deployment Checklist

> Complements `cap-integration` (deploy-approuter-mta.md). Use this skill to *audit* existing
> deployment artifacts for correctness and security before running `mbt build` / `cf deploy`.

Intent2Code uses the **html5-apps-repo pattern** (no approuter module — CLAUDE.md hard rule 2). The
files are generated by `node .claude/skills/sap-conventions/scripts/deploy-config.mjs <app>`, then
`cd <app> && npm install`. A missing or incomplete file is fixed by rerunning it, never by hand. Both
accepted `mta.yaml` layouts are mapped in
[`mta-layouts.md`](../deployment-validation/references/mta-layouts.md).

## The 5 checks

### Check 1 — `mta.yaml` required service bindings

Every CAP + Fiori MTA must bind the correct BTP managed services. Missing bindings cause
runtime auth failures or 502 errors that only appear post-deploy.

**Required resources:**

| Service | Plan | Bound to | Missing if… |
|---|---|---|---|
| `xsuaa` | `application` | CAP srv module, app deployer, destination content module | 401 on every OData call after deploy |
| `destination` | `lite` | CAP srv module, destination content module | Destination name cannot be resolved → 502 |
| `html5-apps-repo` | `app-host` | App deployer (`content-target: true`, `HTML5Runtime_enabled: true`), destination content module | UI never pushed to the repository → 404 |
| `connectivity` | `lite` | CAP srv module | Only needed when a backend is on-premise via Cloud Connector |

There is no `app-runtime` resource and no approuter module: the HTML5 Application Runtime of SAP
Build Work Zone serves the app. **How to check:** Grep `mta.yaml` for `service: xsuaa`,
`service: destination` and `service: html5-apps-repo`, then Read the `requires:` list of the srv
module, the app deployer and the destination content module.

See [`references/mta-structure.md`](references/mta-structure.md) for a fully annotated
`mta.yaml` with all modules and resources, common omissions, and consume-only (no CAP) variant.

### Check 2 — `xs-app.json` security

Each UI app has its own `xs-app.json` (`app/<module>/xs-app.json`, shipped in the app zip). It must
never open CORS (`allowedOrigins: ["*"]`): that lets any website make authenticated requests with
the session of the user. `"*"` = CRITICAL. A missing `allowedOrigins` is fine (same origin only).

**Also check every OData route has `csrfProtection: true` and `authenticationType: "xsuaa"`.**
**How to check:** Grep `app/*/xs-app.json` for `allowedOrigin`, `csrfProtection` and
`authenticationType`; every route except the html5-apps-repo-rt catch-all needs both.

See [`references/xs-app-security.md`](references/xs-app-security.md) for a fully annotated
`xs-app.json`, route ordering rules, and the catch-all pattern for HTML5 repo serving.

---

### Check 3 — OData route completeness in `xs-app.json`

Every OData service the Fiori app calls must have a matching route in `xs-app.json`. A missing
route sends the request to the html5-apps-repo-rt catch-all, which returns a 404.

**Cross-check the BUILT manifest URIs against the routes.** For a CAP app the source manifest
keeps `/odata/v4/<svc>/`; the `relative-odata-uri` build task makes it `odata/v4/<svc>/` in the
built app, which the generated route `^/?odata/(.*)$` matches. **How to check:** Grep
`app/<module>/webapp/manifest.json` for `"uri"`, Grep `app/<module>/xs-app.json` for `"source"`
and `"destination"`, and Grep `app/<module>/ui5.yaml` for `relative-odata-uri`.

The destination name in that route must equal the srv-api destination `Name` in `mta.yaml`
exactly (case-sensitive) — `srv-api` in the generated layout.

### Check 4 — npm dependency audit

Run `npm audit` to detect known vulnerabilities in production dependencies before deploy.

```bash
npm audit --omit=dev --audit-level=high
```

- `--omit=dev` — only production dependencies matter for deployment.
- `--audit-level=high` — exits non-zero for HIGH and CRITICAL vulnerabilities.

**Findings to act on:**

| Level | Action |
|---|---|
| CRITICAL | Block deploy — fix or update the package |
| HIGH | Block deploy — fix before shipping |
| MODERATE | Flag as WARNING — remediate in next sprint |
| LOW | Log — acceptable to defer |

Also check for `--legacy-peer-deps` in any install script in `package.json` or `mta.yaml` build
commands — it hides peer-dependency conflicts that can cause runtime incompatibilities.

---

### Check 5 — CF health-check endpoint

Cloud Foundry requires a reachable health-check endpoint for zero-downtime rolling deploys.
Without it, CF marks the app instance as crashed during restage and rolls back.

For the **CAP service module**, the default `cds serve` exposes `GET /health` automatically.
Verify it is not overridden:
```bash
grep -r "health" srv/ app/  # confirm no route hijacks /health
```

Optionally set the health check explicitly on the srv module (`cds add mta` leaves the CF default,
a port check, which is enough):
```yaml
parameters:
  health-check-type: http
  health-check-http-endpoint: /health
```

## Deployment Checklist

- [ ] No approuter module; `mta.yaml` generated by `deploy-config.mjs` (or a hand-written layout that passes `mta-layouts.md`)
- [ ] `mta.yaml` has the `xsuaa` resource bound to the srv module and the destination content module
- [ ] `mta.yaml` has the `destination` resource bound to the srv module
- [ ] `mta.yaml` has the `html5-apps-repo` `app-host` resource with `HTML5Runtime_enabled: true` on its content target
- [ ] `mta.yaml` has a `connectivity` resource only if a backend is on-premise via Cloud Connector
- [ ] `xs-app.json` has no `allowedOrigins: ["*"]`
- [ ] All OData routes in `xs-app.json` have `csrfProtection: true`
- [ ] All OData routes in `xs-app.json` have `authenticationType: "xsuaa"`
- [ ] Every BUILT manifest `dataSources.uri` matches a `source` regex in `xs-app.json` (CAP: `relative-odata-uri` task in `ui5.yaml`)
- [ ] The route destination equals the srv-api destination `Name` in `mta.yaml` (case-sensitive)
- [ ] `npm audit --omit=dev --audit-level=high` exits 0
- [ ] No `--legacy-peer-deps` in install/build scripts
- [ ] CAP service exposes `/health` and it is not overridden
